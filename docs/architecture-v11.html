Document Expansion LLM

AnythingLLM(v1.16.0) 포크. 사내 한글 문서 아카이브를 근거 기반 QA와 초안 작성으로 확장하는 시스템 — 처음부터 새로 만들지 않고, 기존 오픈소스 구성요소를 재사용한다.

01

4대 목표

방향은 고정, 순서는 실사용에 따라 조정한다 — 자세한 시퀀싱은 §06 참고.

GOAL 1

아카이브 + 자동 분류

PDF·PPT·HWP·DOCX·XLSX 등을 수집하고, 문서 유형·분야로 반자동 분류해 내용을 색인한다.

GOAL 2

범위 한정 근거 QA

수집된 자료 안에서만 답하고, 인용을 클릭하면 원문의 정확한 위치(PDF는 bbox, 그 외는 문단 앵커)를 옆 패널에 띄운다.

GOAL 3

외부 간편 조회

주 사용처는 데스크톱이지만, 급한 조회를 위해 앱/링크로 외부에서도 접근 가능해야 한다.

GOAL 4

템플릿 기반 초안 생성

질문이 주어지면 과거 문서/양식의 형식을 학습해 그에 맞는 초안을 작성하고 저장한다.

02

수집 → 답변 파이프라인

핵심 원칙: 인입 시점(ingest-time) 데이터만 선제 설계한다 — page/bbox/section_path/content_hash/sensitivity처럼 나중에 추가하면 전체 코퍼스를 재파싱·재임베딩해야 하는 값만. API 스키마나 응답 필드는 필요할 때 얼마든지 추가한다.

01업로드multer, 한글 파일명 mojibake 방지 디코딩
→
02파싱docling-serve(PDF/PPTX/ODP/ODT) · hwp-hwpx-parser(.hwp) · OWPML 트리워크(.hwpx)
→
03구조화koStructure.js — 헤딩/아웃라인 레벨 감지, section_path 생성
→
04청킹조/섹션 단위 정렬 청킹, 분할 시 표 헤더 반복
→
05분류claudecli 제안 → 사람 확정(민감도/유형/분야), 불확실은 보류
→
06임베딩BGE-M3 dense, LanceDB 저장 — 워크스페이스 = 민감도 경계
→
07검색벡터 검색 + bge-reranker-v2-m3-ko, 전체 섹션 단위 재구성
→

→
09인용 뷰어pdf.js + bbox 하이라이트, /api/document/raw/:docId

전 구간에서 1단계(파싱)와 4단계(청킹)가 축 — 여기서 페이지 경계와 위치 정보를 보존해야 뒤의 인용 정확도가 성립한다.

03

아키텍처 결정 D1–D8

2026-08-28 확정. 각 결정은 재작업 비용이 큰 인입 시점 선택이라 먼저 고정했다.

D1파싱 스택 = docling-serve공식 Docling FastAPI 사이드카(Python 3.12), 직접 구현 안 함. 외부 파싱 API 없음(Somansa 프록시/오프라인 환경) — 모델은 1회 캐시 후 HF_HUB_OFFLINE.
D2인용 정밀도 = PDF bbox / 그 외 앵커PDF는 정확한 bbox 하이라이트. HWP·DOCX·XLSX는 문단(또는 시트!셀) 앵커까지만. DOCX→PDF 렌더링은 보류.
D3벡터 DB = LanceDB → pgvector(P0b)지금은 LanceDB. 규모가 커지면 WSL2 위 pgvector로 전환(이 머신엔 Docker/MSVC 없음) — 같은 Postgres가 문서 메타/사용자도 보관.
D4HWP 커버리지 = 계층형 폴백① HWPX 네이티브 XML ② .hwp 멀티 파서(hwp-hwpx-parser) ③ LibreOffice headless→PDF→docling(OCR). 문서마다 parse_path/parse_confidence 기록.
D5분류 = 반자동LLM이 doc_type/domain/tags를 제안하고 사람이 확정하거나 다른 체계로 재분류. classify_source 저장. Paperless-ngx 데이터 모델 참고.
D6모델 제공자 = 생성만 교체 가능임베딩(BGE-M3)·리랭커(bge-reranker-v2-m3-ko)·파싱·OCR은 전부 로컬. 생성 LLM만 API로 둘 수 있고 설정으로 교체 가능.
D7한글 어휘 검색 = BGE-M3 sparsePostgres tsvector는 한글 토큰화가 안 됨. 같은 모델이 내는 sparse 출력을 어휘 항으로 사용(dense+sparse 컬럼), pg_bigm은 백스톱.
D8품질 게이트 = 골든 Q&A 회귀50–100개 골든 질문 세트로 채점. 이후 모든 단계의 완료 조건은 "골든 세트 회귀 없음".

왜 아직 "Gemini"가 아닌가

  • AnythingLLM 내장 gemini 제공자 = Google AI Studio API(GEMINI_API_KEY) — 무료 티어는 데이터로 학습, 유료(과금 켠) 티어는 학습 안 함.
  • "Gemini Enterprise" 급 기밀성 보장은 실제로 Vertex AI(GCP 프로젝트 + 서비스 계정)에서 나오는데, AnythingLLM에는 내장 Vertex 제공자가 없음 — claudecli처럼 커스텀 제공자를 새로 만들어야 함.
  • 사용자의 실제 "Gemini Enterprise 계정" 형태(AI Studio 키 / Vertex 프로젝트 / Workspace용 Gemini 구독)가 아직 확인되지 않음 — 확인되는 대로 붙인다.
항상 로컬: 임베딩(BGE-M3), 리랭커(bge-reranker-v2-m3-ko), 파싱/OCR(Docling). 생성 단계만 클라우드로 나간다 — 이 경계는 어떤 계획이든 바뀌지 않는다.
05

분류 체계 — 3개 축

모든 문서는 독립된 세 축으로 분류된다. LLM이 제안하고, /settings/classification 리뷰 화면에서 사람이 확정한다.

규칙 (2026-08-31): 국가가 공개 배포한 문서 — 법률·시행령·시행규칙·예규·고시·지침·가이드라인 등 — 는 일반 범용이다(대외비 아님). 신호: 국가법령정보센터 / 관보 / 부처 홈페이지 출처. 그 외 애매한 문서는 사람이 확정하기 전까지 격리·민감으로 취급한다.

확정 · 이동 · 중복정리 (P4 리뷰 화면)

  • 제안(propose) — claudecli가 문서 텍스트를 읽고 민감도/유형/분야/태그를 1차 제안.
  • 확정(confirm) — 사람이 그대로 받거나 값을 고쳐 저장. 확정 전까지는 자동 라우팅 대상이 아님.
  • 이동(move) — 확정된 민감도와 워크스페이스 티어가 다를 때(티어 불일치), 사람이 수동으로 다른 워크스페이스로 옮김. 자동 라우팅은 하지 않는다 — 사용자가 명시적으로 원한 제약.
  • 중복정리(dedupe) — 같은 워크스페이스에 같은 문서(content_hash)가 두 번 이상 들어간 경우, 어느 사본을 남길지 라디오로 고르고 나머지를 정리.

전체 코퍼스 스캔 결과

  • 손상 문자(U+FFFD, 깨진 글자 표시)를 전체 파싱 결과 파일에서 0건 확인 — mojibake/인코딩 손상 없음.
  • 생태계 같은 흔한 한글 복합어가 코퍼스 전체에서 21회 정확하게 나타남 → 자모/음절 처리 자체는 정상.
  • 표 헤더는 청킹으로 분할될 때도 반복되도록 이미 고쳐짐(5308a652) — 표가 잘려도 컬럼명을 잃지 않음.

발견된 결함 1건 — 국지적, 검색 품질엔 무영향

"...물리적 공간 제약을 넘어서는 'O4O 태계 통합'과..." (원문 추정: 'O4O 생태계 통합' — 음절 "생" 1개 누락)

같은 HWP 문서 안에서 생태계는 21곳 중 20곳에서 정확히 나타나고, 정확히 같은 문장이 반복되는 지점(요약 헤더)에서만 이 형태로 나타남 — hwp-hwpx-parser가 특정 런(run) 경계(개정 마크·인라인 객체 등)를 지나며 앞 글자를 흘리는 것으로 추정. 한 단어 안의 음절 하나이고 주변 문맥이 충분해 답변 품질에는 영향이 없었지만, 근본 원인은 아직 확인 전이다.

결론: 한글은 전반적으로 잘 읽히고 있다 — 인코딩 손상 없음, 구조(조/항, 표, 슬라이드 순서) 보존 양호. 유일한 이슈는 특정 HWP 반복 구절에서의 음절 1개 누락으로, 국지적 파서 결함이지 시스템 전반의 문제는 아니다.
