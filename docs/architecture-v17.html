Document Expansion LLM — v16 이후 작업 정리

1차 프로토타입(v16, 2026-09-11) 이후 실제로 만든 것들을 정리한다. 위쪽은 무엇이 새로 가능해졌는지를 도식으로, 아래쪽은 이번에 바뀐 기술적 내용을 기록한다. 아직 착수하지 않고 방향만 논의한 다음 작업(정기 문서 갱신 작성)은 맨 뒤에 별도로 남겨둔다.

목표 2 근거추적·외부확장 · 목표 3 재설계 서버 테스트 538/538 통과 할루시네이션 방지 원칙 유지 (근거 없으면 "확인 필요") 서버 미확보 · 로컬 PC 한정 운영
00

우리가 만들고자 하는 4단계

처음 기획했던 목표는 4단계다. v16 대비 2단계·3단계의 내용이 깊어졌다.

✓

1단계 · 자동 분류·적재

문서를 올리면 AI가 종류·업무·분야를 제안하고, 사람이 확인만 하면 자동으로 정리돼 보관된다.

완료
✓

2단계 · 자연어 검색·답변

말로 질문하면 근거를 들어 답한다. 이제 어떤 문장이 몇 번 출처에서 왔는지 클릭으로 바로 확인되고, 필요하면 최신 외부 자료까지 더해 답할 수 있다.

완료 + 고도화
●

3단계 · 문서 초안 자동 작성

답변만 근거로 할지, 외부 자료로 보강할지 먼저 고르고, 그 위에 기본/분석 보고서 중 형태를 고르는 2단계 구조로 다시 설계했다.

재설계 · 고도화 중
4

4단계 · 모바일·웹 접근

사무실 PC가 아니어도 어디서든 접속해 검색·확인이 가능해지는 단계.

착수 전
01

이 프로토타입이 할 수 있는 것

v16 시점 기능에, 이번에 새로 생긴 4가지(★)를 더한 현재 시점 기능 목록이다.

📥

업로드만 하면 자동 정리

문서 형태(PDF·워드·엑셀·한글 파일)를 가리지 않고 올리면 AI가 업무 분류·문서 종류·분야를 제안한다. 사람이 확인·확정만 하면 태그가 붙은 채로 아카이브에 쌓인다.

🔍

자연어로 질문, 근거로 답변

관련 문서를 찾아 그 내용만으로 답한다. 문서에 없는 내용은 지어내지 않고 "확인 필요"라고 표시한다.

🎯

★ 출처 번호를 눌러 바로 검증

답변 속 [3] 같은 인용 번호가 클릭 가능한 버튼이 됐다. 누르면 오른쪽 사이드바가 정확히 그 출처로 스크롤·강조돼, "이 숫자가 어느 문서였지?"를 더는 눈으로 찾지 않아도 된다.

🧵

★ 맥락을 이어가는 후속 질문

"그중 A 부분은 법률적으로 문제없어?" 같은 후속 질문을 던지면, 이전 대화를 참고해 독립적인 질문으로 다시 쓴 뒤 검색한다. 원래 검색만으로 부족하면 새 검색 결과를 덧붙여 보완한다.

🌐

★ 필요하면 외부 최신 자료까지 확인

질문창에서 "내부 자료만" / "내부 + 외부 자료"를 고를 수 있다. 관련 법·규제·동향처럼 아카이브에 없을 수 있는 내용은 웹 검색으로 보강해 [브라우징N]으로 구분 표시하고, 클릭하면 실제 웹페이지를 바로 볼 수 있다.

📝

★ 답변→보고서, 2단계로 세분화

"답변 내용만" 또는 "외부자료 보강" 중 자료 범위를 고르고, 그 다음 "기본보고서" 또는 "시사점·동향·리스크까지 담는 분석보고서" 중 형태를 고른다. 조합마다 실제로 다른 절 구성과 내용이 나온다.

🗂️

업무별로 나눠 보기

전체 자료를 하나로 쌓아두되, 화면에서는 전체/실적/법규/대외 같은 업무 관점으로 필터링해서 볼 수 있다.

🛡️

사람이 마지막 확인

분류도, 검색도, 초안도 AI가 제안만 하고 최종 확정·수정은 항상 사람이 한다. 완전 자동화의 오류 위험 없이 반복 작업만 줄이는 구조다.

03

질문을 던졌을 때 답변이 만들어지는 흐름

v16의 4단계 흐름에, 이번에 생긴 "외부 자료 보강" 분기와 "출처 클릭 검증"을 더했다.

예시 질문 · "최근 유통산업발전법 개정 동향과 관련 규제 이슈를 알려줘. 내부 문서에 없는 최신 외부 정보도 같이 찾아줘."
↓
1
(선택) 업무 범위로 좁히기 + 자료 범위 선택
사이드바에서 업무 범위를 고르고, 질문창 위에서 "내부 자료만" / "내부 + 외부 자료"를 고른다.
2
이전 대화가 있으면 독립 질문으로 재작성
후속 질문이면("그중 A는...") 최근 대화 몇 턴을 참고해 그 자체로 이해되는 질문으로 다시 쓴다. 첫 질문이면 이 단계는 건너뛴다.
3
의미로 관련 문서 조각 찾기 + 부족하면 보완
질문을 숫자로 바꿔(임베딩) 아카이브에서 뜻이 가까운 조각을 넓게 찾고, 한 문서가 핵심이면 그 문서에서 더 끌어와 보완한다.
4
★ "외부 + 내부" 선택 시 — 웹 검색도 함께 수행
내부 검색과 별개로 키워드 없는 웹 검색을 돌려 관련 페이지를 찾는다. 결과는 [브라우징N]이라는 별도 이름표로, 내부 인용([n])과 절대 섞이지 않게 붙인다.
5
AI(Claude)가 근거만으로 종합
모아온 문서 조각(+외부 자료)만 근거로 답을 작성한다. 근거에 없는 내용은 "확인 필요"로 표시한다.
↓
답변 · 내부 근거는 [1][2], 외부 근거는 [브라우징0]처럼 구분해 표시된다. 어떤 번호든 클릭하면 오른쪽 사이드바가 정확히 그 출처로 이동한다 — 내부 문서면 원문 위치, 외부 자료면 실제 웹페이지가 그 자리에서 열린다.
실제 라이브 테스트에서 이 정확한 질문으로 확인했다: 내부 문서에 없는 내용임을 스스로 인지하고, 웹 검색으로 국회입법현황·법령정보센터 등 5개 페이지를 찾아 답을 구성했다.
04

v16 이후 만든 것 — 순서대로

v16(1차 프로토타입 보고) 이후 실제로 커밋된 작업을 순서대로 정리했다.

🔗
인용 추적 개선

"[9]번이 어느 문서인지 찾기 어렵다" 피드백 해결

답변 속 인용 번호를 실제 클릭 가능한 버튼으로 바꾸고, 누르면 정확히 그 출처가 강조되며 사이드바가 열리도록 함. 상세는 §07.

🧵
후속 질문 보완 로직

맥락을 이어가는 후속 질문 지원

"그중 A 부분은..." 같은 후속 질문이 엉뚱한 곳을 검색하지 않도록, 이전 대화를 참고해 독립 질문으로 재작성 + 원래 검색이 부족하면 추가 검색으로 보완하는 로직을 붙임. 상세는 §08.

🌐
내부 + 외부 자료 검색

아카이브에 없는 최신 법·규제·동향까지 확장

질문창에 자료 범위 토글을 추가하고, 키 없는 웹 검색을 붙여 답변에 최신 외부 정보를 더할 수 있게 함. 내부·외부 인용을 별도 이름표로 분리하고, 외부 결과는 실제 웹페이지를 보여주는 뷰어를 새로 만듦. 상세는 §09.

📝
초안 작성 재설계

"보고용/대외기관용" → "자료 범위 × 문서 유형" 2축 구조로

기존 단순 유형 선택을 걷어내고, 자료 범위(답변만/외부보강)와 문서 유형(기본/분석)을 독립된 두 축으로 다시 설계. 외부보강 시 웹 검색 기능을 재사용해 보고서 내용을 확장. 상세는 §10.

🎨
브랜드 · UI 정리

실사용 피드백 기반 화면 정리

기본 아이콘/워드마크가 원본 오픈소스(AnythingLLM)와 동일해 보인다는 피드백으로 새 심볼로 교체. 실제 기능 차이가 없거나 오해를 주는 버튼·문구 다수 제거. 상세는 §11.

05

지금 필요한 것 · 지금의 한계

v16에서 "조사 중"이던 문제 하나가 해결됐고, 새 기능 2개(외부검색·초안 확장)에서 생긴 한계가 새로 추가됐다.

필요한 자원

항목현재 상태비고
작업 환경(PC)팀원 개인 Windows PC, 메모리(RAM) 제한적변화 없음 — v16과 동일한 제약
운영 서버미확보 — 지금은 개인 PC에서만 실행정책지원팀 전체가 실사용하려면 서버(또는 클라우드) 배정 필요
사내망 인증서(CA)확보·적용 중이 PC의 회사 네트워크는 TLS를 가로채는 사내 인증서를 쓴다. 웹 검색 기능의 외부 요청이 처음엔 이 인증서를 안 믿어 전부 실패했고, 서버 실행 시 인증서 경로를 함께 지정해야 한다는 걸 이번에 다시 확인함(§09).
Google Gemini API미승인 · 미발급변화 없음 — 스캔 이미지 문서 인식용, v16과 동일하게 대기 중
Claude(Anthropic) API/CLI확보·사용 중분류·답변·후속질문 재작성·초안 작성·검색어 추출까지 전부 이걸로 동작
해결됨: v16에서 "초안 생성이 간헐적으로 실패"한다고 조사 중이던 문제의 원인을 찾았다 — 새 기능이 아니라 Anthropic 계정의 사용량(요청 빈도) 제한에 걸린 것이었는데, 기존 코드가 그 에러 내용을 버리고 뭉뚱그린 메시지만 보여줘서 원인을 알 수 없었다. 실패해도 실제 에러 내용을 그대로 보여주도록 고쳐서, 다음에 같은 문제가 생기면 바로 원인을 알 수 있게 됐다.

새로 생긴 한계

웹 검색은 "화면을 읽어오는" 방식 — 안정성에 한계구조적 한계
별도 검색 API 계약 없이, 검색 사이트 화면을 그대로 읽어와 결과를 뽑아내는 방식(스크래핑)이다. 그 사이트가 화면 구조를 바꾸면 결과를 못 뽑아낼 수 있다 — 실제로 테스트 중 그런 경우를 하나 발견해 고쳤다(§09). 정식 검색 API를 쓰면 더 안정적이지만 별도 비용·계약이 필요하다.
초안의 docx·xlsx 내보내기준비 중
v16과 동일 — 지금도 HTML로만 내려받을 수 있다.
모바일·웹 접근(목표 4)착수 전
v16과 동일 — 목표 1·2·3에 어느 정도 안정성이 확보된 뒤 착수할 계획.
정기 문서 갱신 작성설계만 논의, 착수 전
전년도 완성 문서 + 신규 기준으로 새해 보고서 초안을 자동으로 채워주는 기능. 방향은 확인했으나 규모가 커서 이번 버전에는 넣지 않고 다음 단계로 미뤄뒀다 — 상세는 §14.
06

v17 변경 개요

v16(1차 프로토타입 완성 보고, 2026-09-11) 이후 커밋된 5개 작업. 근거 추적 개선 1건, 후속질문 보완 로직 1건, 내부+외부 자료 검색(웹서치) 1건, 문서 초안 작성 재설계 1건, 브랜드·UI 정리 1건.

  • 답변 속 [n] 인용 번호를 클릭 가능한 버튼으로. 상세 §07.

v17-B 후속질문 보완 로직 — c062c4cf

  • 질의 재작성(query condensation) + 보완 검색 병합. 상세 §08.

07

인용 추적 개선

배경: 답변 속 [9] 같은 인용 번호가 사이드바에 나열된 출처 목록과 순서가 다르게 매칭되어, 사람이 눈으로 세어가며 찾아야 했다("여기 마지막 [9]항목은 어느 문서 어떤 곳에서 가지고 왔는지 보기가 쉽지 않다").

원인

모델에게 알려주는 인용 번호(contextTexts 배열의 위치)와, 사이드바가 보여주는 출처 목록(제목별로 중복 제거된 Citations 목록)이 서로 다른 배열이었다. 번호는 첫 배열 기준인데 화면은 두 번째 배열 기준으로 그려져, 숫자와 실제 항목이 어긋났다.

수정

  • stream.js에서 sources를 sources.map((s,i) => ({...s, citationIndex: i}))로 번호를 직접 찍어 보냄 — 모델이 쓰는 번호와 소스 배열의 인덱스가 항상 같다는 걸 코드로 보장.
  • 프론트 linkifyCitationMarkers()가 렌더링된 답변 텍스트에 남아있는 [n] 문자를 정규식으로 찾아 <button data-citation-idx="n">로 바꿔치기 — 마크다운이 이미 링크(<a>)로 바꾼 부분은 건드리지 않아 안전.
  • 메시지 wrapper에 클릭 위임 핸들러를 달아, 버튼 클릭 시 citationIndex로 사이드바를 열고 정확히 그 항목을 스크롤·강조(findCombinedSourceByFocus).
이 구조가 §09의 외부 검색 인용([브라우징N])에도 그대로 확장됐다 — 같은 focus 객체에 browsingIndex라는 별도 이름표만 추가해서 재사용.
08

후속질문 보완 로직

배경: "그중 A란 부분과 법률적 부분에 검토돼야 할 사항이 있을까?" 같은 후속 질문은 그 문장만 놓고 검색하면 엉뚱한 결과가 나온다 — "A"가 뭘 가리키는지 검색 엔진은 모른다.

설계

  • 질의 재작성(condenseFollowupQuery): 대화 기록이 있을 때만, 최근 6턴을 참고해 LLM 호출 1번으로 "그것", "위 내용" 같은 지시어를 구체적인 명사로 풀어 독립적인 질문으로 다시 씀. 이미 독립적인 질문이면 그대로 반환(자기 최적화). 대화 기록이 없는 첫 질문이면 이 단계 자체를 건너뛰어 비용을 아낌.
  • 보완 로직(mergeFollowupSearchResults): 재작성된 질문으로 검색해도 결과가 빈약할 때를 대비해, 원래 질문으로도 한 번 더 검색해 "새로 찾은 것만 덧붙이는" 방식으로 병합. 순서를 바꾸거나 기존 결과를 덮어쓰지 않는다 — pgvector 자체의 #mergeLexicalAdditions와 같은 철학을 한 단계 위(두 검색 결과 합치기)에 적용한 것.
실제 라이브 확인: "GS리테일 기후위기 대책은?" → "그중 A 부분과 법률적 부분에 검토돼야 할 사항이 있을까?"로 이어지는 대화에서, 재작성된 질문이 원래 대화의 구체적인 항목명을 가리키는 것으로 정확히 바뀌었고 검색도 그 항목에 맞게 좁혀졌다.
09

내부 + 외부 자료 검색

배경: "관련 법이나 규제 검토가 필요한데, 그 법이 어디서 생겨날지 모르고 우리가 다 파악해서 아카이빙하지 못하는 경우가 많다" — 아카이브에 없는 내용은 원래 이 시스템 설계상 "확인 필요"로만 표시되는데, 그중 일부는 웹에서 바로 찾을 수 있는 정보다.

2

5

설계

  • 검색: server/utils/webSearch/index.js — 별도 계약·API 키 없이, 검색 사이트의 결과 화면(HTML)을 그대로 읽어와 제목·요약·링크를 뽑아내는 방식. 기존에 에이전트 스킬용으로만 있던 같은 원리의 코드(web-browsing.js)에서 추출해 일반 채팅에서도 쓰게 함.
  • 인용 이름표 분리: 내부 인용은 citationIndex([n]), 외부 인용은 완전히 별도인 browsingIndex 네임스페이스([브라우징n])로 나눠 절대 번호가 섞이지 않게 함. 외부 검색 결과는 시스템 프롬프트 문자열에 직접 덧붙여, 모델이 자동으로 붙이는 번호 매기기와 충돌하지 않게 함.
  • 출처 화면: [브라우징N]을 클릭하면 사이드바가 열리고, 내부 문서처럼 텍스트만 보여주는 게 아니라 실제 웹페이지를 iframe으로 그대로 띄운다. 일부 사이트는 iframe에 띄우는 걸 막아두는데, 6초 안에 로딩이 안 끝나면 "새 탭에서 열기" 버튼으로 자동 전환.
  • UI: 질문창 위에 "내부 자료만" / "내부 + 외부 자료" 토글 2개 버튼.
테스트 중 발견 및 수정 — 파싱 버그: 검색 결과 화면에서 제목·링크를 뽑아내는 정규식이 "링크 속성이 항상 특정 순서로 나온다"고 가정하고 있었다. 직접 만든 단위 테스트가 이 가정과 다른 순서의 예시로 실패하면서 발견 — 실제 검색 사이트 마크업도 이 순서를 보장하지 않는다. 순서에 상관없이 찾아내는 방식으로 고쳤고, 같은 버그가 있던 기존 에이전트 스킬 코드도 함께 수정했다(원본 코드를 그대로 가져다 썼기 때문에 같은 결함이 있었다).
테스트 중 발견 및 수정 — 인증서 문제: 서버를 재시작했더니 웹 검색이 전부 fetch failed로 죽었다. 직접 해당 주소로 요청을 날려보니 SELF_SIGNED_CERT_IN_CHAIN 에러 — 이 회사 네트워크가 쓰는 사내 인증서를 새로 띄운 서버 프로세스가 모르고 있었던 것. 서버를 실행할 때 그 인증서 경로(NODE_EXTRA_CA_CERTS)를 함께 넘겨줘야 한다는 걸 재확인하고 반영했다.

알려진 이슈

  • 초안 생성 간헐적 실패 (v16에서 조사 중 → 해결) — 원인은 새 기능 버그가 아니라 Anthropic 계정의 사용량 제한(rate limit)이었다. claude -p 하위 프로세스가 429 에러를 내도 기존 코드가 그 내용을 버리고 뭉뚱그린 메시지만 보여줘 원인 파악이 어려웠던 것 — 실패 시에도 실제 에러 내용을 파싱해 그대로 보여주고 RATE_LIMITED로 표시하도록 수정.
  • 웹 검색의 구조적 한계 — 키 없는 스크래핑 방식이라 대상 사이트의 화면 구조 변경에 취약하다. 테스트 중 실제로 한 번 걸려 수정했다(§09).
  • 초안의 docx·xlsx 내보내기 — v16과 동일, 버튼은 있으나 비활성. HTML만 동작.
  • 고성능 임베딩(bge-m3) 미사용 — v16과 동일, 이 로컬 PC의 메모리 한계로 경량 모델(e5-small) 유지 중.
  • 서버 미확보 — v16과 동일, 팀원 개인 PC에서만 실행.

💡 무엇을 하려는 것인가

예시 1 — 지속가능보고서: 2025년까지 완성한 보고서가 아카이브에 있고, 2026년판 작성에 착수하려 함. 올해 새로 생긴 기준·가이던스를 반영해, 작년 문서의 구조·양식을 뼈대로 삼아 초안을 다시 씀 — 이때 지속가능보고서 작성 목적이 아니었던 다른 업무용 자료도 근거로 함께 활용.

예시 2 — 공정거래 협약이행평가: 기존 제출 자료는 쌓여 있지만 새해 제출은 처음부터 다시 작성해야 하는 상황. 새 기준을 넣고, 기존 제출 자료를 기반으로 작성 가능한 부분을 채움.

공통 요구사항: 근거가 부족한 부분은 [자료 필요]로 표시. 이는 (1) 아카이브에 그동안 얼마나 쌓였는지 절별로 확인하는 동시에, (2) 이미 있는 자료를 관계 부서에 또 요청하는 일을 막는 효과가 있음.

🧭 제안한 흐름 (논의만, 미구현)

입력 3가지: ① 기준 문서(작년 완성 문서, 문서함에서 선택) ② 신규 기준/가이던스(업로드 또는 텍스트) ③ 아카이브 전체(항목마다 다시 검색)

목차 추출→ 절별 신구 비교(LLM 1회)→ 절별 아카이브 검색→ 절별 근거 기반 작성→ 조립 · 미리보기 · 다운로드

목차 추출은 문서 chunk에 이미 있는 section_path로 별도 파싱 없이 가능. 절별 작성 시 "근거 부족 → 확인 필요" 원칙(§10)을 그대로 [자료 필요]로 확장. 진입점은 문서함에서 "새 버전 작성" 형태를 제안했음.

⚠️ 미리 확인해둔 한계

절이 많은 문서(연차보고서 등)는 절마다 검색+생성을 반복해야 해서 LLM 호출이 많아지고 생성 시간이 길어짐 — 진행 상황을 보여주는 화면이 필요. 신규 기준 문서가 표·조항처럼 구조가 뚜렷할수록 "무엇이 새로 생겼는지" 판단이 정확해지고, 산문 형태로 모호하면 판단이 다소 느슨해질 수 있음.
