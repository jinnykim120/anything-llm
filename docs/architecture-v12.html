Document Expansion LLM

AnythingLLM(v1.16.0) 포크. 사내 한글 문서 아카이브를 근거 기반 QA와 초안 작성으로 확장하는 시스템 — 처음부터 새로 만들지 않고, 기존 오픈소스 구성요소를 재사용한다. 이 문서는 초기 Claude 설계안(v9, 2026-08-31)과 이후 GPT로 이어받은 구현 기록(v11, 2026-09-02)을 하나로 합친 통합본이며, 2026-09-07 실제 구동·회귀 재검증에서 발견한 결함 2건(claudecli ENAMETOOLONG, pgvector 메모리 가드)을 그 자리에서 수정하고 재검증까지 반영했다.

pgvector dense 검색 정상 동작 확인 claudecli ENAMETOOLONG 수정 완료 BGE-M3 · bge-reranker-v2-m3-ko 랜딩·워크벤치·문서함 UI 구현 D:\ai factory\auto docu\anything-llm
01

4대 목표 · 현황

방향은 고정, 순서는 실사용에 따라 조정한다 — 자세한 시퀀싱은 §08 참고. AnythingLLM 베이스에서 이미 확보된 것과, 이 프로젝트가 새로 메운 공백을 구분한다.

GOAL 1

아카이브 + 자동 분류

PDF·PPT·HWP·DOCX·XLSX 등을 수집하고, 문서 유형·분야로 반자동 분류해 내용을 색인한다.

GOAL 2

범위 한정 근거 QA

수집된 자료 안에서만 답하고, 인용을 클릭하면 원문의 정확한 위치(PDF는 bbox, 그 외는 문단 앵커)를 옆 패널에 띄운다.

GOAL 3

외부 간편 조회

주 사용처는 데스크톱이지만, 급한 조회를 위해 앱/링크로 외부에서도 접근 가능해야 한다.

GOAL 4

템플릿 기반 초안 생성

질문이 주어지면 과거 문서/양식의 형식을 학습해 그에 맞는 초안을 작성하고 저장한다.

AnythingLLM이 이미 주는 것 vs 비어 있던 것 (2026-08-31 진단, 지금도 유효)

목표이미 있던 것비어 있던 것 → 현재 상태
1 · 아카이브 + 자동 분류collector가 PDF·DOCX·XLSX·PPTX·EPUB·오디오·이미지 파싱, 워크스페이스 단위 문서 관리, 폴더HWP/HWPX 미지원, 자동 분류 없음 → 둘 다 구현 완료(P3 HWP 레이어드 파싱, P4 분류·검수 UI, confirmedBy까지)
2 · 근거 답변 + 원본 위치근거 검색 + 소스 스니펫(title/text/score), 인용 목록 UI, SourcesSidebar위치 메타 없음, 하이브리드 검색 없음 → 위치 메타(page/bbox/section_path) 관통 완료, pgvector dense 검색 정상 동작 확인(§10)
3 · 외부 접속anythingllm-embed, anythingllm-mobile, 멀티유저 + API 키 + RBAC리버스 프록시/터널 구성만 하면 됨 → P5, 아직 착수 전(우선순위 낮음, 언제든 가능)
4 · 초안 작성에이전트 빌더, 슬래시 커맨드, 프롬프트 변수, 워크스페이스 메모리, 스케줄 작업전용 작성 기능 없음 → P6 Compose, 아직 미착수(위 프리미티브 조합으로 설계만 확정)
02

설계 원칙 — 단일 핵심 변경

이 시스템의 성패는 한 가지 파이프라인 변경에 달려 있었다. 나머지 작업은 모두 이 위에 얹히는 additive 변경이다. (Claude 설계안 v9, 2026-08-28 확정 — 지금까지도 이 축을 기준으로 모든 단계가 정렬돼 있다.)

THE ONE CHANGE THAT MATTERS — 파싱 → 청킹 → 벡터 저장 → 채팅 소스 → 프론트 뷰어까지 청크마다 위치 메타데이터(page, bbox, section_path)를 관통시킨다. 원래 collector의 asPDF/index.js는 pageContent.join("")로 페이지 경계를 버리고, server의 TextSplitter.splitText()가 그 평문을 잘랐다 — 이 두 지점을 바꾸는 것이 전체 프로젝트의 척추였다(P1a·P1b·P2에서 완료).

부수 원칙 (지금까지 유지됨)

  • 인입 시점 데이터만 선반영한다. 파싱·임베딩 시점에 계산되는 것(page·bbox·section_path·content_hash·sensitivity·context_prefix)은 처음부터 채운다 — 나중에 추가하면 전체 코퍼스 재파싱·재임베딩이 필요한 유일하게 비싼 왕복이기 때문이다. 반대로 API 엔드포인트·응답 필드(classify API, answer.meta, feedback 테이블)는 선반영하지 않는다 — 나중에 붙여도 데이터 마이그레이션이 없다.
  • 파서는 사이드카로. Node 스택은 그대로, Python 파싱은 docling-serve(네이티브 Python 3.12 venv) 프로세스로 격리 — .local-cache/docling-venv에 실제로 설치·기동됨.
  • 비-PDF의 정확 위치는 스코프 축소. PDF만 좌표 하이라이트, HWP·XLSX·DOCX는 문단/시트-셀 앵커.
  • 자동 분류는 반자동. LLM 제안 → 검수 화면에서 확정 또는 재분류(P4, confirmedBy까지 완결).
  • 측정 가능하게. 리트리벌·청킹·프롬프트를 건드리기 전에 골든셋 + 평가 하네스(P0.5a)를 먼저 세운다 — eval/.
  • 생성 LLM 전략은 상시 재검토. 원래는 "격리 워크스페이스=Ollama 로컬 상시 에어갭 / 일반 워크스페이스=Gemini Enterprise" 2-티어였으나, 2026-08-31에 claudecli 단일 제공자로 전환됐다(§06 참고) — 임베딩·리랭커·파싱·OCR은 지금도 항상 로컬이라는 하드 경계만 유지.

04

아키텍처 결정 D1–D8

2026-08-28 확정, 이후 실사용 결과로 갱신. 각 결정은 재작업 비용이 큰 인입 시점 선택이라 먼저 고정했다.

D1파싱 스택 = docling-serve공식 Docling FastAPI 사이드카(Python 3.12), 직접 구현 안 함. 외부 파싱 API 없음(Somansa 프록시/오프라인 환경) — 모델은 1회 캐시 후 HF_HUB_OFFLINE. .local-cache/docling-venv에 실제 설치·기동 확인.
D2인용 정밀도 = PDF bbox / 그 외 앵커PDF는 정확한 bbox 하이라이트. HWP·DOCX·XLSX는 문단(또는 시트!셀) 앵커까지만. DOCX→PDF 렌더링은 보류.
D3벡터 DB = pgvector 전환 완료LanceDB로 시작해 WSL2 확보 후 pgvector로 전환. server/.env.development에서 VECTOR_DB=pgvector가 실제 활성값이고, HNSW 인덱스(createIndexSql)·dense 검색·rerank 경로·lexical fallback·섹션 확장까지 구현(server/utils/vectorDbProviders/pgvector/index.js, 1,300줄+). 단위테스트로 로직 검증, run-local.ps1의 WSL2 자동기동으로 운영 검증. 배포 템플릿(.env.example, docker/.env.example)은 여전히 LanceDB가 기본값(신규 클론이 즉시 뜨도록 의도적으로 유지)이지만, pgvector로 전환하는 주석 블록에 이 환경에서 실제로 쓰는 NATIVE_EMBEDDING_MIN_FREE_MEMORY_MB까지 포함해 갱신했다(2026-09-07). 메모리 가드 수정(2026-09-07): 이전에는 NATIVE_EMBEDDING_MIN_FREE_MEMORY_MB 기본값(2560MB)이 이 머신의 실제 여유 메모리보다 높아 dense 임베딩 로드가 매번 거부되고 lexicalSearchResponse() 폴백으로만 검색됐다. server/.env.development에 NATIVE_EMBEDDING_MIN_FREE_MEMORY_MB="1600"을 추가해 리랭커 임계값과 맞추자, 서버 로그에서 "Insufficient free memory" 경고가 완전히 사라지고 dense 검색이 정상 동작함을 확인했다(회귀: eval/run.mjs 계속 통과, eval/answers.mjs 8/8, eval/perf.mjs archive-full 0 errors). §10 리스크 항목은 해결로 갱신.
D4HWP 커버리지 = 계층형 폴백① HWPX 네이티브 XML ② .hwp 멀티 파서(hwp-hwpx-parser) ③ LibreOffice headless→PDF→docling(OCR). 문서마다 parse_path/parse_confidence 기록.
D5분류 = 반자동 확정 완료LLM이 doc_type/domain/tags를 제안하고 사람이 확정하거나 다른 체계로 재분류. classify_source 저장. 확정 시 confirmedBy(사용자 ID) + updatedAt(확정시각)까지 Prisma 스키마·API·검수 화면(DocRow.jsx)에 완결 구현. Paperless-ngx 데이터 모델 참고.
D6모델 제공자 = 생성만 교체 가능임베딩(BGE-M3)·리랭커(bge-reranker-v2-m3-ko)·파싱·OCR은 전부 로컬. 생성 LLM만 API로 둘 수 있고 설정으로 교체 가능 — 현재는 claudecli가 실제 활성 provider(§06).
D7한글 어휘 검색 = lexical fallbackPostgres tsvector는 한글 토큰화가 안 됨. 원래 설계는 BGE-M3의 sparse 출력을 항상 병합하는 진짜 하이브리드였으나, 실제 pgvector 구현은 dense 검색이 비었을 때만 한국어 조사 제거 로직을 갖춘 ILIKE 기반 lexical 검색으로 전환하는 폴백 구조로 단순화됐다(lexicalSearchResponse()). 항상 점수를 융합하는 진짜 dense+sparse RRF는 아직 미구현 — 후속 후보(§09).
D8품질 게이트 = 골든 Q&A 회귀골든 질문 세트로 채점. 이후 모든 단계의 완료 조건은 "골든 세트 회귀 없음". eval/run.mjs(검색 지표) + eval/answers.mjs(답변 품질, claudecli judge).

왜 아직 "Gemini"가 아닌가

  • AnythingLLM 내장 gemini 제공자 = Google AI Studio API(GEMINI_API_KEY) — 무료 티어는 데이터로 학습, 유료(과금 켠) 티어는 학습 안 함.
  • "Gemini Enterprise" 급 기밀성 보장은 실제로 Vertex AI(GCP 프로젝트 + 서비스 계정)에서 나오는데, AnythingLLM에는 내장 Vertex 제공자가 없음 — claudecli처럼 커스텀 제공자를 새로 만들어야 함.
  • 사용자의 실제 "Gemini Enterprise 계정" 형태(AI Studio 키 / Vertex 프로젝트 / Workspace용 Gemini 구독)가 아직 확인되지 않음 — 확인되는 대로 붙인다.
항상 로컬: 임베딩(BGE-M3), 리랭커(bge-reranker-v2-m3-ko), 파싱/OCR(Docling). 생성 단계만 클라우드로 나간다 — 이 경계는 어떤 계획이든 바뀌지 않는다.

fork 유지비. 파서·검색·프론트 확장을 가능한 한 새 파일 + 훅으로 구현하고, 기존 파일 수정은 최소화. 정기 rebase가 필요하나 별도 자동화는 아직 없음.
인용 정확도 (LLM이 근거 밖 내용 생성)측정 체계 있음
엄격 인용 프롬프트 + 답변 품질 평가(eval/answers.mjs, judge=claudecli)로 faithfulness·completeness·citation_accuracy를 상시 측정. §10의 ENAMETOOLONG·메모리 가드 수정 후 재검증한 골든 8문항 기준 mean faithful 0.994·complete 1.0·cite-acc 0.994, 8/8 임계치 통과. 다만 심판이 claudecli 자신이라 이중검증(별도 judge)까지는 아니다.
멀티도메인 검색에서 관련 없는 분야 혼입부분 대응
domain·doc_type 메타 필터 + 리랭커. 질문에서 분야를 추정해 사전 필터링하는 에이전트 라우팅은 아직 후보 단계(§08 다음 후보).
사이드카·임베딩 서버가 늘며 실행 복잡도 증가상시 관리
docling-serve + pgvector(WSL2) + (선택)Langfuse. run-local.ps1이 서비스 기동·헬스체크를 담당하도록 유지. 프로덕션 배포용 compose 파일 통합은 아직 없음.

대안 검토 결론 (v9 원문, 지금도 유효)

  • kotaemon 베이스 — 인용-뷰어 UX가 제품의 전부라면 이미 완성돼 있음. 단 Gradio/Python, 멀티유저·API·위젯·모바일·에이전트 스토리가 약함. 컴포넌트 접근 방식만 차용.
  • RAGFlow 베이스 — 딥-닥 파싱·청크 투명성 최고, 그러나 ES·MySQL·Redis·MinIO로 스택이 무겁고 Docker 전용. DeepDoc 파서와 청킹 규칙의 공급원으로만 사용.
  • R2R (SciPhi) / Morphik — 프로덕션 인입·하이브리드·지식그래프(R2R), 페이지 이미지 임베딩(Morphik)이 강점. 베이스 교체는 아니고 부품·아이디어 공급원: R2R의 지식그래프는 P6 후보, Morphik의 비주얼 검색은 P3.5 후보(현재 보류).
  • Onyx — 40+ 커넥터가 강점이나, 사용자가 아카이브를 직접 올리는 이 시나리오엔 과함. 외부 소스 연동이 필요해지면 재검토.
  • PaperQA2 / Paperless-ngx — 각각 근거 인용 정확도, 문서 아카이브 데이터 모델의 레퍼런스. 코드가 아닌 패턴을 P2·P4에 반영(완료).
결론(유지): 멀티유저·API·위젯·모바일·에이전트·MIT·Node 스택 일치를 종합하면 AnythingLLM 유지가 우세. 파싱은 docling-serve, 인용 UX는 kotaemon 패턴, 정확도는 PaperQA2 패턴, 분류는 Paperless-ngx 모델, 한국어 모델·평가 하네스로 보강 — 이 조합을 그대로 실행해 지금 상태에 도달했다.
