방향 전환 — 종합 진단 후 재구축

v11–v13은 "위치 메타 관통 + 분류 + pgvector + 엑셀 무결성"을 국소적으로 하나씩 쌓아왔다. 그 과정에서 stock AnythingLLM의 단순한 검색 위에 커스텀 로직이 5겹으로 얹혔고, 실사용에서 자연어로 물어보면 필요한 자료가 안 나온다는 핵심 문제가 드러났다. v14는 국소 패치를 멈추고 검색·적재·삭제를 종합적으로 다시 세운다. 프로토타입으로 선보여 서버·API 예산을 받는 것이 목표이므로, xlsx·pdf·word·hwp 4종이 모두 확실히 도는 것이 완료 기준이다.

검색: 5겹 파이프라인 자기충돌 임베딩 조용한 실패 → 키워드 검색 강등 방향: 단일 워크스페이스 + 태그 뷰 임베딩: bge-m3 → multilingual-e5-small sensitivity 프로토타입 보류 docling-optional
01

왜 이 문서인가

v13까지의 작업은 개별적으로는 다 맞았지만, 합쳐놓으니 goal 2(근거 QA)의 검색 품질이 무너졌다. 사용자 판단: "국소적인 검토 말고 종합적인 검토 및 수정이 필요한 시점. 기존에 가져와 붙인 것도 재검토해서 필요없거나 작동 안 하면 과감히 쳐내도 된다. 적재된 자료 전부 지우고 새로 올려도 문제 없다."

핵심 증상 (사용자 진술): ① 분류·저장은 잘 되는데 goal 2에서 자연어로 검색하면 그 자료가 잘 안 나온다 (가장 큰 문제). ② 같은 파일을 올리면 적재에 문제가 생긴다. ③ 시스템에서 지운 적재 파일이 안 지워진다. ④ 지금은 엑셀만 확인하는데 엑셀·PDF·워드·HWP가 전부 잘 돌아야 한다.
02

목표 대비 위치

4대 목표 중 1·2번을 가볍게 완성하는 것이 현재 사정거리다. 3·4번은 그 다음. v14의 모든 작업은 1·2번을 실제로 작동하게 만드는 데 집중한다.

GOAL 1 · 지금

정리 안 된 사내 자료를 올리면 자동 분류 → 확정 → 태깅된 형태로 아카이빙

자료 이력관리이자 항목별 효율적 적재 시스템. 분류/저장 자체는 동작 중. 남은 문제: 적재 안정성(같은 파일, 삭제, 파일타입별 추출 품질).

GOAL 2 · 지금

아카이빙된 자료 기반, 할루시네이션 없는 자연어 검색 + 근거 원문 확인

여러 자료를 합쳐 답하고 각 답의 근거를 눈으로 본다. 유관부서 반복 요청의 업무 비효율 제거. 현재 최대 리스크 — 검색이 필요한 자료를 못 찾음.

GOAL 3 · 나중

비정형/정형 문서 자동 작성

제공 대상별로 과거 자료를 학습해 양식에 맞는 초안·기초틀 생성. 과거 결정사항·수치를 불러옴.

GOAL 4 · 나중

앱/웹으로 외근·미팅 중 근거 자료 확인

다양한 상황에서 자료 근거 기반 초동 대응.

정책지원팀 시나리오: 동반성장·공정거래·대외기관 요청 대응을 위해 정책지원팀이 전사 자료를 아카이빙해 쓴다. 사용 범위·팀·로데이터가 늘수록 추출 정확도가 올라가는 구조로 설계한다.
03

진단 — 검색이 안 되는 이유

stock AnythingLLM 검색은 쿼리 임베딩 → 코사인 top-N → 끝으로 단순하다. 이 fork는 server/utils/vectorDbProviders/pgvector/index.js의 performSimilaritySearch에 커스텀 로직 5겹(한글 lexical fallback / CPU 리랭커 / 스프레드시트 exact-match 우선 / 섹션 확장 / 최종 재정렬)을 얹었고, 이들이 서로 싸운다. 원본 대비 +598줄.

① #preferLexicalDataMatches 가 의미검색 결과를 밀어낸다제거 예정
질문에 숫자가 하나라도 들어있거나(/\d/.test(term)) 출하량·생산량·판매량·수량·금액·실적 중 한 단어라도 있으면, 키워드(SQL ILIKE '%단어%') 매칭 결과에 priority: 2를 주고 의미검색 결과(priority: 1) 위에 강제 배치한다. 이 코퍼스의 실제 질문 상당수가 여기 걸린다("2024년 우리동네GS 실적…"). 게다가 키워드 점수는 합성값(0.35 + 단어겹침비율 × …)이라 실제 bge-m3 코사인(~0.4–0.6)보다 높게 나오고, 뒤이은 "점수순 정렬 후 topN 자르기"에서 의미검색 결과가 잘려나간다. → 자연어 질문인데 키워드 순위 결과가 돌아온다.
② dense 임베딩이 조용히 죽고 검색 전체가 키워드로 강등된다명시적 에러로 전환
쿼리 임베딩이 실패하면 catch가 로그만 남기고 삼킨 뒤 searchResult가 비어 lexicalSearchResponse(ILIKE)로 넘어간다. 2026-09-10 실측: 이 머신 여유 메모리 1,698MB, 임베딩 가드 1,600MB — 거의 항상 아슬아슬. 쿼리 임베딩 한 번에 4.8초(콜드). 다른 프로세스가 100MB만 잡아도 dense가 거부되고, 에러 없이 키워드 검색이 된다. "면류 업계 상황"으로 물으면 "국수 시장 동향" 문서를 못 찾는다.
③ 테스트 워크스페이스가 전부 rerank 모드기본 off
archive-test·archive-full·eval 이 vectorSearchMode: "rerank". 매 질문마다 CPU 크로스인코더(bge-reranker-v2-m3-ONNX)를 돌려서 eval/FINDINGS.md 기준 avg 7.6초, p95/max 최대 22초. 사용자가 말한 "reranker 락"이 이것. rerank는 옵트인 정밀 모드로만 남기고 기본은 dense.
④ 섹션 확장이 최종 truncate와 싸우고, 문서 다양성이 없다재작성
expandSections가 한 섹션의 형제 청크를 끌어온 뒤, 마지막 블록이 전체를 점수순 재정렬해 topN(=12)으로 자른다. 확장 청크는 score = min(히트 점수)라 다시 잘려나가 기능이 반쯤 무효화된다. 또 문서별 청크 수 제한이 없어 topN을 한 문서 청크로 다 채우기도 한다 → "여러 자료를 합쳐서 답변"이 안 된다.
⑤ similarityThreshold 0.25 가 bge-m3 코사인 기준으로 빡빡하다~0.15로
한글 관련 청크가 코사인 0.2–0.3에 자주 걸리는데 threshold 0.25에서 후보에도 못 든다.

진단 — 적재 · 삭제 문제

증상원인 (파일:함수)조치
같은 파일이면 적재 실패 server/models/documents.js addDocuments — existingSourceNames: 기존 문서 중 제목/docSource/파일명이 하나라도 겹치면 말없이 건너뜀. 내용이 달라도, 수정본이어도. 사내자료는 붙임.pdf·보고서.pdf 천지. 파일명 중복차단 제거. content_hash(동일 텍스트) 중복만 유지 + UI에 표면화 + "그래도 추가" 옵션.
적재가 들쭉날쭉 적재 경로 2개. addDocuments(상대경로 저장, 파일명+해시 중복검사) vs server/jobs/embedding-worker.js(native embedder, 절대경로 저장, 해시 중복검사만). native가 활성 경로라 대부분 절대경로로 저장됨. 공유 헬퍼로 한 경로로 통일. docpath는 항상 상대경로.
지웠는데 안 지워짐 removeDocuments — 벡터 삭제가 실패해도(deleteDocumentFromNamespace가 에러를 삼키고 false 반환) 반환값을 무시하고 DB 행을 지운다. 디스크의 파싱 원본(storage/documents/)과 vector-cache/*.json은 안 지운다 → 재업로드 시 stale 캐시가 되살아난다. 벡터 삭제 검증 + 파싱파일·캐시까지 삭제. "워크스페이스 재구축" 관리 액션 추가.
엑셀 추출 부실 collector/processSingleFile/convert/asXlsx.js convertToPipeTable — 헤더 감지가 사용자의 면류 샘플 문자열로 하드코딩됨("구분", "직접생산", "대기업 OEM", /출하량|생산|OEM|연도/). 다른 엑셀엔 안 먹는다. 테스트 하나 통과시키던 코드. 일반 헤더 감지로 재작성. 워크북 1개 = 문서 1개, 시트 = block_type:table 블록으로 finalizeBlocksDoc 경유.
PDF/DOCX 구조 상실 DOCLING_AUTOSTART=false (collector .env.development). PDF→pdf.js(표·목차 없음), DOCX→langchain 텍스트 로더(구조 없음). 그런데 검색 설계가 section_path에 의존(contextual prefix + 섹션 확장) → 대부분 비어있다. HWP/HWPX는 자체 파서라 영향이 덜하다. docling-optional 확정. pdf.js 헤딩 감지 강화, DOCX→mammoth. docling은 중요 문서 수동.

진단 — 인프라 제약

1.7GB
여유 물리 메모리 (총 15.7GB)
1.6GB
bge-m3 임베딩 로드 가드 — 여유와 거의 같음
4.8s
쿼리 1건 임베딩 시간 (콜드)
2,582
현재 pgvector 벡터 수 (archive-full 2,440 + archive-test 136 + eval 6), 1024d

이 박스는 이 워크로드에 메모리가 부족하다. WSL2 Postgres는 223MB로 작고 node 서버들도 idle 126MB인데, 여유가 1.7GB뿐이라 개발 도구 몇 개만 열어도 임베딩 로드가 거부된다. bge-m3의 ONNX 런타임 피크(~1.7GB)가 이 여유와 정면 충돌한다.

결론: bge-m3(1024d)는 이 머신에서 신뢰할 수 없다 — "검색 실패가 너무 많다"(사용자). 프로토타입 기간에는 더 작은 다국어 모델로 내리고, 서버에 붙일 때 bge-m3로 복귀한다.

방향 전환 — 결정 5건

2026-09-10, 전부 사용자 승인.

V1 단일 워크스페이스 archive + 태그 기반 "업무별 뷰" 전사 자료를 벡터 네임스페이스 1개에 다 넣는다. 워크스페이스를 쪼개지 않는다(복사본 0, 재적재 1회 → 더 가볍다). 분류 태그(work_type/domain/doc_type/tags)가 보기 필터 역할: 검색 시 필터 태그 → 해당 문서의 doc_id allow-list → 벡터 쿼리에 WHERE metadata->>'doc_id' = ANY(...) 한 줄 추가. SQLite document_classifications가 원본이라 재분류해도 재임베딩 불필요 — 매 검색 시 최신 태그로 목록만 다시 뽑는다. UI: 채팅 헤더에 업무 선택 드롭다운, 문서함은 이미 축별 그룹핑.
V2 프로토타입에서 sensitivity 축 보류 tier 라우팅 / held=대외비 취급 / 워크스페이스 tier 불일치 플래그 / 수동 tier-move 전부 비활성화. 컬럼은 dormant로 남긴다. 실제 접근통제가 필요해지면 그때 confidential만 별도 네임스페이스로 분리(지금 구조 변경 없이 추가만). 현재 인입 자료는 대부분 "국가 공개배포 = 일반"이고 정책지원팀 한 팀이 쓰므로 지금은 불필요.
V3 임베딩 Xenova/bge-m3 (1024d) → MintplexLabs/multilingual-e5-small (384d) ~487MB, transformers.js v2에 이미 등록됨(server/utils/EmbeddingEngines/native/constants.js), 프리픽스 query:/passage: — native embedder가 이미 처리. 한글 품질은 약간 낮아지지만 메모리 여유가 크고 빨라서 조용한 폴백이 안 터진다. 서버 이전 시 bge-m3 복귀. 모델 교체 ⇒ 전체 재임베딩(클린 슬레이트라 무방).
V4 docling-optional, 경량 파서 강화 DOCLING_AUTOSTART=false를 기본 상태로 받아들인다. pdf.js 헤딩 감지(폰트 크기/볼드 → block_type: heading + 얕은 section_path) 강화, DOCX는 mammoth로 교체(HTML → 헤딩/리스트/표). docling은 중요 문서 수동 옵트인. 이 머신에서 느리고 불안정했던 이력.
V5 과감한 재작성 — 국소 패치 중단 performSimilaritySearch + 적재/삭제를 다시 짠다. eval/run.mjs(검색 지표) + eval/answers.mjs(답변 품질)로 회귀 검증. "국소 패치로는 지금 상태를 못 벗어난다."

08

재구축 계획 P0–P5

각 단계 완료 조건은 "eval 회귀 없음". 사용자가 테스트할 수 있는 첫 지점은 P1 종료 시.

P0 클린 슬레이트 + 모델 교체

  • 임베딩 EMBEDDING_MODEL_PREF → MintplexLabs/multilingual-e5-small, 모델 프리다운로드
  • 초기화: pgvector 전 네임스페이스 drop, workspace_documents·document_vectors·document_classifications 비우기, storage/documents/*·storage/vector-cache/* 삭제, 껍데기 워크스페이스 삭제
  • 워크스페이스 archive 1개 생성 (topN 12, threshold ~0.15, vectorSearchMode default)
산출: 깨끗한 단일 워크스페이스 + 안정적으로 로드되는 임베딩 모델

P1 검색 재작성 — 핵심 수정

  • performSimilaritySearch를 명확한 파이프라인으로: 쿼리 임베딩(query: 프리픽스) → 임베딩 실패 시 명시적 에러(조용한 키워드 강등 금지) → dense 코사인 광역 후보(K≈60) → 문서별 청크 상한(doc_id당 3) → lexical 합집합 보강만(dense가 놓친 문서를 뒤에 추가, dense 순위 불변) → topN 절단 → 마지막에 보수적 섹션 확장(재절단 없음)
  • #preferLexicalDataMatches 삭제. threshold 기본 0.25 → 0.15 (스키마 + workspace.js validator)
  • vectorSearchMode 기본 default, archive에도 default. rerank는 옵트인
  • 메타데이터 필터 파라미터(filterDocIds) 추가 — 업무별 뷰의 additive WHERE 절
  • eval/run.mjs + eval/answers.mjs로 검증 (모델·워크스페이스 갱신 후)
산출: 자연어 질문이 올바른 문서를 여러 개에 걸쳐 반환. 사용자 첫 테스트 지점.

P2 적재 단일화 + 중복 정리

  • addDocuments의 파일명 중복차단 제거. content_hash(동일 텍스트) 중복만 유지 + 반환값 표면화 + force 옵션
  • embedding-worker.js도 상대경로 저장. 공유 createWorkspaceDocumentRow() 헬퍼로 두 경로 통일
  • removeDocuments 완결: 벡터 삭제 검증 → 파싱 원본 폴더 삭제 → vector-cache 항목 삭제 → document_vectors 삭제
  • 관리자 액션 "워크스페이스 재구축": 벡터 nuke + storage/documents/에서 재임베딩. 자료가 꼬였을 때 원클릭 초기화
산출: 같은 파일 재업로드 예측 가능, 삭제가 진짜 삭제, 꼬였을 때 복구 버튼

P3 파일 타입 4종 견고화 (xlsx · pdf · docx · hwp)

  • XLSX: 워크북 1개 = 문서 1개. 시트 → block_type:"table" 블록, section_path = 시트명. 일반 헤더 감지(텍스트 위주 행 다음에 숫자/짧은 행). finalizeBlocksDoc 경유 → content_hash·section_path·표헤더반복·원본보존 자동. sheet-.json 충돌 클래스 소멸
  • PDF: pdf.js 경로 — 텍스트 런의 폰트크기/볼드로 헤딩 감지 → 얕은 section_path. OCR-skip 프로브 유지. RapidOCR는 "image-only" 마커로 대체
  • DOCX: langchain DocxLoader → mammoth(HTML → 헤딩/리스트/표에서 블록 생성)
  • HWP/HWPX: 자체 파서 유지, 실제 파일 3–5개로 검증. HWP_RENDER/render_path 제거
  • 타입별 E2E: 실제 파일 → 업로드 → 파싱 → 청킹 → 임베딩 → 자연어 질의 검색 → 답변 인용
산출: 4종 전부 업로드→검색→인용까지 통과. 프로토타입 시연 가능 상태.

P4 "업무별 뷰" 필터 + sensitivity 해체

  • 백엔드: 검색 엔드포인트가 workTypes 수신 → document_classifications에서 contentHash → workspace_documents에서 docId → filterDocIds
  • 채팅: 활성 업무 필터를 워크스페이스/스레드에서 전달. 프론트: 채팅 헤더 업무 선택기
  • sensitivity: held/tier/라우팅 로직 제거, 컬럼 dormant. 분류기가 sensitivity 필수 요구 해제
산출: 전 자료 검색 + 업무별로 좁혀보기, 둘 다 동작

P5 실제 코퍼스 재적재 + 검증

  • _samples/에서 대표 세트(PDF/DOCX/XLSX/HWP 혼합 ~30–50개)를 archive에 적재
  • eval/ 골든셋을 새 워크스페이스 + 모델로 갱신
  • eval/run.mjs + eval/answers.mjs 실행. 목표: 4종에서 자연어 질의가 올바른 문서 반환, 다중 문서 답변 동작
  • architecture v15로 갱신
산출: 측정된 근거와 함께 goal 1·2 기능 완성

  • 위치 메타 관통 (v9 THE ONE CHANGE) — page/bbox/section_path가 파싱→청킹→저장→소스→뷰어를 관통하는 척추. P1a·P1b·P2의 성과.
