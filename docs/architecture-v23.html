NEXUS(넥서스) — v23 시스템 소개

정책지원팀의 자료 정리·검색·활용을 돕기 위해 만든 사내 문서 아카이브 + AI 질의응답 + 문서 작성 시스템(구 Document Expansion LLM → Recode → 2026-09-21 NEXUS(넥서스)로 리브랜딩). N·Neural — 내·외부 데이터를 신경망처럼 유기적으로 연결 / E·Expert — 자료를 파악·분석해 활용 / X·eXact — 할루시네이션 없는 정확한 Fact 기반 검증 / U·Understanding — 원천 수집부터 논리적 추론까지 심층 이해 / S·Solutions — PPT·Word 문서·정책 제안 등 새로운 시각 도출. 위쪽은 무엇을 할 수 있는지 도식으로 소개하고, 가운데는 지금 상태와 한계를, 아래쪽은 기술 아키텍처를 기록한다.

NEXUS 리브랜딩 · 호출량 관리 · 생성문서 메타 상속 · PPT 레이아웃 다양화(6종 + 후처리) 실코퍼스 91문서 · 서버 테스트 707 통과 할루시네이션 방지 원칙 — 근거 없으면 "확인 필요", 통계 수치는 실제 계산만 인용 서버 미확보 · 로컬 PC 한정 운영
00

우리가 만들고자 하는 4단계 · 지금 어디까지 왔나

처음 기획했던 목표는 4단계다. 1·2단계는 완료했고, 3단계(문서 작성 + 분석)는 계속 확장 중이다.

✓

1단계 · 자동 분류·적재

문서를 올리면 AI가 종류·업무·분야를 제안하고, 사람이 확인만 하면 자동으로 정리돼 보관된다.

완료
✓

2단계 · 자연어 검색·답변

질문하면 근거를 들어 답한다. 출처 번호를 눌러 바로 검증하고, 필요하면 최신 외부 자료까지 더해 답하며, "우리회사" 같은 표현도 문맥에 맞는 계열사로 정확히 해석한다.

완료 + 고도화
●

3단계 · 문서 작성 + 분석

① 답변 하나를 보고서로 바로 만들기, ② 작년 문서 + 신규 기준으로 올해 문서 전체를 다시 채워 넣기, ③ 빈양식을 주면 그 서식을 채우기(원본 파일 그대로도 가능), ④ 미리 모아둔 문서함 폴더로 참고자료 범위 좁히기, ⑤ 만들어진 결과물이 다시 아카이브 원자재로 순환, ⑥ 지정한 자료 전체에서 수치를 빠짐없이 추출, ⑦ 실제 통계 계산으로 회귀·군집·예측 서술, ⑧ 스레드에 자료를 고정해 매 답변에 반영, ⑨ PPT를 그래프·5개 테마로 더 품질 있게.

진행 중
4

4단계 · 모바일·웹 접근

사무실 PC가 아니어도 어디서든 접속해 검색·확인이 가능해지는 단계.

착수 전
01

이 시스템이 할 수 있는 것

지금 시점에서 실제로 쓸 수 있는 기능 전체를 한눈에 정리했다.

📥

업로드만 하면 자동 정리

PDF·워드·엑셀·한글 파일을 가리지 않고 올리면 AI가 업무 분류·문서 종류·분야를 제안한다. 사람이 확인만 하면 태그가 붙은 채로 아카이브에 쌓인다.

🔍

자연어로 질문, 근거로 답변

관련 문서를 찾아 그 내용만으로 답한다. 문서에 없는 내용은 지어내지 않고 "확인 필요"라고 표시한다.

🎯

출처 번호를 눌러 바로 검증

답변 속 [3] 같은 번호가 클릭 가능한 버튼이 된다. 누르면 원문의 정확한 위치가 사이드바에 열린다.

🧵

맥락을 이어가는 후속 질문

"그중 A 부분은…" 같은 후속 질문도 이전 대화를 참고해 정확히 찾아낸다.

🌐

필요하면 외부 최신 자료까지

아카이브에 없을 수 있는 최신 법·규제·동향은 웹 검색으로 보강하고, [브라우징N]으로 구분해 표시한다.

📝

답변을 그 자리에서 보고서로

답변 내용만 쓸지 외부자료로 보강할지, 정리만 할지 시사점·동향·리스크까지 분석할지 — 2축으로 골라 바로 만든다. 블록을 클릭해 그 부분만 다시 쓰게 할 수도 있다.

🏢

전사문서작성tool — 작년 문서 갱신 + 빈양식 채우기

작년 문서를 뼈대로 삼아 절별로 다시 채우거나, 빈 서식을 그대로 올려 그 항목들을 채운다. 미리 모아둔 문서함 폴더로 참고자료 범위를 좁힐 수도 있다. 부족한 자료는 [자료 필요]로 표시하고 바로 요청서로 뽑는다.

🧮

(신규) 통계분석 — 실제 계산만, AI는 숫자를 안 만든다

문서 초안에서 문단을 클릭해 "통계분석"을 요청하면, 그 문단·업로드 자료의 숫자를 실제 Python 통계 라이브러리(scikit-learn/statsmodels)로 계산한 값만 서술한다. 수요예측·이탈예측·세분화·구매가능성 등 회사 실제 업무에 맞춘 4개 대표 모델 + 15개 방법 중 직접 고르거나, "미정"으로 두면 목적에 맞는 방법을 자동으로 고른다.

🗂️

(신규) 자료 추출하기 — 지정한 문서 전체를 빠짐없이

빈 질문창에서 "자료 추출하기"를 누르면, 새로 올린 자료나 문서함 폴더를 지정해 유사도 검색(top-K)을 거치지 않고 그 문서들을 하나하나 통째로 훑어 수치·핵심 사실을 빠짐없이 뽑아 정리한다. 보도자료·외부 PDF 몇 개에서 관련 수치만 모아 정리할 때 특히 유용하다.

📌

(신규) 우선 자료 — 이 스레드엔 항상 반영

답변 아래에서 특정 자료(업로드 파일 또는 아카이브 문서)를 "우선 자료"로 고정하면, 그 스레드의 이후 모든 답변이 유사도 순위와 무관하게 그 자료를 항상 근거로 포함한다.

🏷️

(신규) "우리회사" 자동 구분

질문이나 근거 문서에 "우리회사"처럼 모호한 표현이 나오면, 문맥에 따라 GS리테일(그룹)·GS25(편의점)·GSSHOP(홈쇼핑)·GSFRESH(수퍼)를 구분해 답한다 — 모든 질의응답·초안·통계분석·자료추출에 공통 적용.

📊

(신규) PPT 품질 개선

표만 넣던 것에서 실제 막대·선·원형 그래프를 그리는 PPT로, "AnythingLLM으로 제작됨" 워터마크는 제거, 슬라이드 하나에 내용이 몰리면 자동으로 다음 장으로 나눠준다. 5개 테마 중 1개(첫 장 두 색을 그대로 표·강조색에 쓰던 것과 안 맞던 "기업형" 테마)의 색상 불일치를 바로잡았다.

🎯

검색이 태그·키워드까지 함께 본다

벡터 유사도만으로는 표·목록 같은 내용이 순위 밖으로 밀리곤 했다. 질문 키워드와 사람이 확정한 분류 태그가 일치하면 가산점을 줘서, 진짜 필요한 내용이 더 잘 올라온다.

🔄

만들어진 자료가 다시 원자재로

초안·전사문서작성tool 결과를 다운로드하면 "내부생성자료" 폴더에 자동 보관된다. 단, 분류 검수에서 사람이 확인(승인)하기 전까지는 검색에 절대 쓰이지 않는다.

📃

HTML 말고 다른 형식으로도

초안·전사문서작성tool 결과를 실제 워드(DOCX) 파일로도 받을 수 있다. 빈양식을 채운 경우엔 업로드한 원본 파일 그 자체에 값을 삽입해 서식을 그대로 유지한 채 내려받을 수도 있다(DOCX만 — HWP는 미지원).

🛡️

사람이 마지막 확인

분류도, 답변도, 초안도, 통계 계산 방법도 AI가 제안만 하고 최종 확정·수정은 항상 사람이 한다.

02

어떤 도구로 만들었나

개발은 팀원 개인 컴퓨터에서, 아래 도구들을 조합해 진행했다. 가운데 "Orca"가 전체 작업을 조율하고, AI 코딩 에이전트(Claude Code)가 실제 코드 작성·설치·테스트·문서화를 맡는다.

화살표는 "이 도구가 Orca(작업 조율)로 투입되어 함께 쓰인다"는 뜻이다. 오픈소스(AnythingLLM)를 베이스로 포크해 우리 것으로 개조했다 — 처음부터 새로 만들지 않고, 검증된 기반 위에서 아카이브·질의응답·문서작성·통계분석 기능을 쌓아 올렸다.

04

질문을 던졌을 때 답변이 만들어지는 흐름

아카이브 내부 자료만으로 답하는 기본 흐름이다.

예시 질문 · "2025년 GS리테일의 국수 출하량은? 그중 가장 많은 출하량 제품은 무엇이고, 국수 출하량이 강제되는 이유는 뭐야?"
↓
1
(선택) 업무 범위로 좁히기
사이드바에서 "실적"·"법규"처럼 범위를 골라두면 그 범위의 문서로만 검색을 좁힌다.
2
후속 질문이면 독립 질문으로 재작성
"그중 A는…" 같은 질문은 최근 대화를 참고해 그 자체로 이해되는 질문으로 다시 쓴다.
3
의미로 관련 문서 조각 찾기 + 보완
질문을 숫자로 바꿔(임베딩) 아카이브에서 뜻이 가까운 조각을 넓게 찾고, 부족하면 추가로 보완한다. "우선 자료"(§06)를 고정해뒀다면 이 결과에 항상 합쳐진다.
4
AI(Claude)가 근거만으로 종합
모아온 문서 조각만 근거로 답을 작성한다. "우리회사" 같은 모호한 표현은 회사 용어집(§20)으로 구분하고, 근거에 없는 내용은 "확인 필요"로 표시한다.
↓
답변 · 실적 수치와 근거 조항이 함께 제시되고, 각 문장 옆에 [1][2] 처럼 출처 번호가 붙는다. 번호를 클릭하면 원문의 정확한 위치가 열려 눈으로 재검증할 수 있다.
05

내부 + 외부 자료를 함께 쓰면

관련 법·규제·동향은 언제 어디서 새로 생길지 모르고, 그걸 전부 미리 아카이빙해두는 건 불가능하다. 이럴 때를 위한 확장이다.

1
질문창에서 자료 범위 선택
"내부 자료만" / "내부 + 외부 자료" 중 고른다. 안 고르면 항상 내부만.
2
내부 검색은 그대로 실행
§04와 동일하게 아카이브 전체에서 근거를 찾는다.
3
★ "외부" 선택 시 — 웹 검색도 함께 실행
키 없는 웹 검색(DuckDuckGo)으로 관련 페이지를 찾는다. 별도 계약·API 키 없이 동작한다.
4
근거를 이름표로 구분해 결합
내부는 [1][2], 외부는 [브라우징0][브라우징1] — 절대 서로 섞이지 않는다.
5
AI가 두 근거를 함께 종합해 답변
내부 자료와 외부 자료를 모두 참고해 하나의 답을 만든다.
실제 라이브 확인: "최근 유통산업발전법 개정 동향을 알려줘. 내부 문서에 없는 최신 정보도 찾아줘"라는 질문에, 내부 문서에 없다는 걸 스스로 인지하고 웹 검색으로 국회입법현황·법령정보센터 등 5개 페이지를 찾아 답을 구성했다. [브라우징N]을 클릭하면 사이드바에 실제 웹페이지가 그대로 열린다.

왜 필요한가

  • 새 법·규제·가이드라인이 어디서 생길지 미리 알 수 없어, 아카이브만으로는 항상 최신 상태를 유지하기 어렵다.
  • "순수 내부 자료 기반 답변"과 "내부 + 외부 이슈까지 파악한 답변"을 상황에 맞게 선택할 수 있다.
  • 답변마다 어떤 문장이 내부/외부 근거인지 항상 구분되어 표시되므로, 신뢰도를 스스로 판단할 수 있다.
06

(신규) 우선 자료로 고정해서 반영하기

§04의 검색은 매번 "이 질문에 뜻이 가장 가까운 조각"을 새로 찾는다 — 보통은 맞지만, 특정 자료를 이 대화 내내 계속 참고하게 하고 싶을 때는 맞지 않는다. 우선 자료는 이 스레드에 한해 그 문제를 해결한다.

1
답변 아래 자료 목록에서 "우선 자료로 고정" 선택
이번 대화에서 새로 업로드한 파일이든, 아카이브에 이미 있는 문서든 상관없이 고정할 수 있다.
2
스레드 상단에 고정 자료 칩으로 표시
지금 이 대화에 어떤 자료가 강제로 반영되고 있는지 항상 눈에 보인다. 필요 없어지면 칩에서 바로 해제.
3
이후 모든 답변이 유사도 순위와 무관하게 포함
§04의 3단계 검색 결과에 고정 자료가 항상 합쳐진다 — 벡터 유사도가 낮아 원래는 topN 밖으로 밀렸을 자료도 빠지지 않는다.
업로드 파일을 고정하는 절반은 AnythingLLM 원본에 이미 있던 기능(workspace_parsed_files + stream.js)을 그대로 썼다. 이번에 추가한 건 아카이브에 이미 있는 문서를 고정하는 나머지 절반이다(§17).

08

(신규) 자료 추출하기 — 지정한 자료에서 수치를 빠짐없이

§04의 검색은 "질문과 뜻이 가까운 조각"만 상위 몇 개(top-K)를 가져온다 — 빠르지만, "이 문서들에 나온 수치를 전부 정리해줘" 같은 요청에는 맞지 않는다. 유사도 순위 밖으로 밀린 숫자가 조용히 빠질 수 있기 때문이다. 자료 추출하기는 그 문제를 피하려고 지정한 문서 전체를 유사도 검색 없이 하나하나 순회한다.

1
빈 질문창(대화 시작 전)에서 "자료 추출하기" 선택
첫 화면의 아카이브 액션 중 하나로 노출된다.
2
범위 선택 — 새 업로드 / 문서함 폴더 / 둘 다
그 자리에서 새로 파일을 올리거나, 이미 아카이브에 있는 문서함 폴더를 지정하거나, 둘을 함께 쓸 수 있다.
3
문서 하나하나를 통째로 훑어 추출
청크 단위 유사도 검색이 아니라 문서 원문 전체를 근거로, 숫자·핵심 사실을 문서별로 정리한다.
4
결과를 채팅으로 확인 · 이어서 활용
정리된 결과를 그대로 §07 문서 작성으로 이어가거나, §09 통계분석의 근거 자료로 쓸 수 있다.
보도자료나 외부 PDF 몇 개를 업로드하고 "여기서 수치만 따로 정리해줘" — 이 기능을 만들게 된 실제 질문이었다. RAG 방식의 top-K 검색은 "관련성 높은 조각"을 찾는 데는 강하지만 "이 자료 안의 모든 수치"를 보장하지는 않는다는 한계를 정확히 겨냥해 설계했다.
09

(신규) 통계분석 — AI는 숫자를 만들지 않는다

일반 LLM에게 "이 데이터로 회귀분석 해줘"라고 시키면, 그럴듯하지만 실제로 계산되지 않은 숫자를 답할 위험이 있다. 이 기능은 그 위험을 구조적으로 없앤다 — 숫자를 만드는 단계는 오직 실제 Python 통계 라이브러리 계산 하나뿐이고, AI는 그 앞뒤(파라미터 추출 · 결과 서술)만 맡는다. PPT는 정보 밀도상 이 기능을 붙이지 않았다 — HTML 초안에서만 제공한다.

1️⃣
문서 초안에서 문단 클릭

"이 부분 통계분석 해줘" 요청

예: "이 매출 추이로 회귀분석 해줘. 가정값은 OO야" 처럼 자연어로 요청.

2️⃣
분석 방법 선택 — 6가지 방식

4개 대표 모델 + 15개 방법 드롭다운 + "미정"

회사 실제 업무와 맞닿은 4개를 앞에 고정 노출(아래 표) — 나머지 11개는 드롭다운, 확신이 없으면 "미정"을 고르면 LLM이 목적에 맞는 방법을 스스로 판단해 고른다.

3️⃣
(선택) 보충 자료 업로드

문단 근거만으로 부족하면 파일 추가

PDF·엑셀·워드·HWP 등 형식 제한 없이 올릴 수 있다(§08 자료 추출하기와 같은 범용 업로드 경로 재사용) — 이번 분석에만 쓰고 아카이브에는 저장되지 않는다.

4️⃣
자동 처리 — LLM 추출 → Python 계산 → LLM 서술

숫자를 지어내는 단계는 없다

① LLM이 근거에 실제로 적힌 숫자만 {data, params}로 뽑고(부족하면 "자료 필요"로 중단), ② Python(scikit-learn/statsmodels)이 진짜 계산을 수행하고, ③ LLM이 그 계산 결과 JSON에 있는 숫자만 인용해 문단으로 서술한다.

5️⃣
결과 반영

클릭했던 그 문단이 분석 결과로 교체

§07의 클릭-수정 흐름을 그대로 재사용 — 별도 화면 전환 없이 초안 안에서 바로 확인한다.

4개 대표 모델 — 회사 실제 업무 기준으로 선정

수요예측
시계열 기반 판매량·발주량 예측 (시계열예측)
이탈예측
회원·거래처 이탈 가능성 분류 (분류모델)
세분화
고객·상품 군집으로 그룹 나누기 (군집분석)
구매가능성
특정 상품·프로모션 반응 확률 (회귀/분류)

나머지 11개(회귀분석·군집분석·시계열예측·분류모델·몬테카를로 시뮬레이션 등)는 드롭다운에서 직접 고를 수 있다.

설계 의도: 3단계 파이프라인 중 숫자가 생성되는 지점은 Python 계산 딱 한 곳이다. 앞의 LLM은 "근거에 있는 숫자만 뽑기"(없으면 멈춤), 뒤의 LLM은 "계산된 숫자만 인용해 서술하기"로 역할이 좁게 제한되어 있어, 두 LLM 호출 중 어느 쪽도 새로운 수치를 만들어낼 여지가 없다.

분류 체계

6개 축(민감도/업무분류/사업부/문서종류/분야/태그)으로 AI가 제안하고 사람이 확정한다. taxonomy.js가 기준값의 단일 소스다.

  • 값 삭제 UI — 각 드롭다운에 삭제 버튼. 확정된 문서가 그 값을 쓰면 건수를 안내하며 차단한다.
  • 기본 정렬 — "미확정 먼저"로, 검수 화면에 들어가면 처리할 문서가 항상 위에 보인다.
  • 사업부 목록에서 전사·유통BU·정책지원팀·기타를 정리 — 실제 조직 단위(홈쇼핑BU·편의점BU·수퍼마켓BU)만 남겼다.
  • DocumentClassification.confirm() — 사람이 직접 확정하거나(검수 화면), §21처럼 이미 확정된 값을 그대로 물려받아 즉시 확정할 수도 있다.
  • 업로드자 팀명 — 이 인스턴스는 로그인이 없어(멀티유저 모드 꺼짐, 계정 0개) "누가 올렸는지"를 자동으로 남길 방법이 없다. 대신 자료 업로드 팝업에 "업로드한 팀명" 입력을 필수로 추가해 workspace_documents.uploadedByOrgUnit에 기록하고, 검수 화면의 "업로드자:" 표시가 여기 연결된다.
  • (발견·수정한 버그) 일괄 확정 태그 소실 — POST /classification/confirm-bulk가 항상 tags:[]를 함께 보내 선택한 문서 전체의 태그를 매번 지우고 있었다(confirm()은 tags가 undefined일 때만 그 칼럼을 안 건드리는데, 명시적 []는 값으로 취급됨). 확정 79건 중 74건 영향, 72건은 AI 재분류로 복구. 일괄 확정은 이제 태그를 절대 건드리지 않는다.

검색 하이브리드 리랭크

GS25 계약서의 필수품목 표가 자연어 질문("구입 필수 품목을 알려줘")에 대해 벡터 유사도만으로는 같은 문서 안 다른 조항보다 순위가 낮아, topN(당시 12) 밖으로 밀려 답변에서 빠지는 일이 실제로 있었다. performSimilaritySearch(모든 검색이 거치는 핵심 함수 — 채팅/쿼리, 전사문서작성tool 근거검색, 자료 추출하기, 우선 자료 병합까지 전부 포함)를 이렇게 고쳤다.

  • 키워드 + 태그 가산점: 벡터 후보를 최종 순위로 확정하기 전에, 질문 키워드가 청크 본문에 얼마나 겹치는지(+12%) 그리고 문서의 확정된 분류 태그에 얼마나 겹치는지(+15%, env로 조정 가능)를 벡터 점수에 가산한다. 사람이 확정한 태그이므로 원본 벡터 유사도보다 신뢰도를 조금 더 준다. PGVector.tagsForDocIds()가 청크의 doc_id → workspace_documents → content_hash → document_classifications.tags를 이어 붙인다.
  • 1등 문서 전체 포함 (버그 수정): 기존에도 "1등 문서는 청크 개수 제한 없이 가져온다"는 로직이 있었으나, 그 뒤 topN으로 다시 한 번 통째로 잘라내는 코드가 이 우대를 무력화시키고 있었다 — 지금 수정으로 1등 문서 몫은 지켜지고, 그래도 다른 문서를 위한 최소 슬롯은 항상 남겨둔다.
  • topN 12 → 25 (archive-full 워크스페이스) — 위 두 수정과 함께 여유 폭을 넓혔다.
수정 중 발견한 부작용: "1등 문서는 무제한"을 실제로 무제한으로 풀어주자, 특정 질문 표현에서 임베딩 모델이 전혀 무관한 문서 하나에 200개 넘는 후보 전부를 몰아주는 경우가 실제로 있었다(재현 확인됨) — 그 문서가 결과를 통째로 차지해버렸다. 1등 문서 허용량에 상한(최대 30)을 두고, 키워드 매칭(lexical) 구제 결과를 위한 슬롯을 항상 최소한 확보하도록 다시 수정해 해결했다.

종단 검증: 수정 전 표 항목이 topN 밖(21~25위)에 있어 "구체적인 목록은 문서에 없다"고 잘못 답하던 것이, 수정 후 표 12개 항목 전부를 정확히 인용하는 답변으로 바뀜을 확인. 단위테스트 27개(하이브리드 부스트 + 1등문서 보존 케이스 포함) + 서버 전체 604개 통과.

(신규) 통계분석 파이프라인 (기술)

server/endpoints/statsAnalysis.js — POST /workspace/:slug/stats/analyze. 숫자를 만드는 단계는 오직 2단계(Python)뿐이라는 원칙으로 설계했다.

  • 1단계 · LLM 추출(buildExtractMessages): 사용자 요청 + 방법(또는 "auto") + 근거 텍스트/업로드 자료에서 그 방법이 필요로 하는 {method, data, params}를 JSON으로만 뽑는다. 근거에 없는 수치는 절대 채우지 말고 {"missing_data": "..."}로 응답하도록 프롬프트에 명시. 15개 방법의 데이터/파라미터 모양은 server/utils/stats/methodSchemas.js가 단일 소스.
  • 2단계 · Python 실계산(runAnalysis, server/utils/stats/): hwp_extract.py와 같은 subprocess 호출 관례를 따라, docling-venv에 설치한 scikit-learn/statsmodels/scipy로 run_analysis.py가 실제 계산을 수행하고 결과 JSON을 돌려준다.
  • 3단계 · LLM 서술(buildNarrativeMessages): 2단계 결과 JSON에 있는 숫자만 인용해 마크다운으로 서술 — 반올림 외의 방식으로 숫자를 바꾸지 않도록 프롬프트에 명시. p-value 등 통계적 유의성은 일반 독자가 이해할 수 있게 짧게 풀어 설명.
  • 결과 반환 모양: draft.js의 /revise-block과 동일한 {revised} 형태로 돌려줘, 프론트가 이미 갖고 있던 블록 패치 흐름(§16)을 그대로 재사용한다.
  • 보충 자료 업로드: 처음엔 클라이언트에서 직접 CSV만 파싱하는 방식으로 좁게 시작했으나, "보통 CSV만 넣진 않는다"는 지적을 계기로 §18과 같은 parseUploadEphemeral 범용 경로로 교체 — PDF·엑셀·워드·HWP 등 형식 제한이 없어졌다. uploadedDataBlock()이 {text}(신규, 일반 파싱 결과) 형태를 우선 처리하고, 옛 {rows}(CSV 전용) 형태도 하위 호환으로 계속 지원한다.
  • 회사 용어집 연동: 1·3단계 시스템 프롬프트 모두에 §20 COMPANY_GLOSSARY를 덧붙여, 추출·서술 과정에서도 "우리회사" 같은 표현이 올바른 계열사로 해석되게 한다.

전사문서작성tool (기술)

목차 추출

  • extractOutlineFromBlocks() — 청크의 section_path 메타데이터로 절을 나눈다. 커버리지가 30% 미만이면(예: 구조 인식이 약한 docx) null을 반환해 다음 방식으로 넘긴다.
  • extractOutlineViaLLM() — 모델에게 원문을 다시 쓰게 하지 않고, 각 절이 "이 구절로 시작한다"는 경계 마커만 받아 원문(pageContent)에서 직접 잘라낸다 — 원문이 그대로 보존된다.
  • 기준 문서를 여러 개 고르면(다중 선택) 문서별 목차를 순서대로 이어붙인다.

신구 비교 · 절 작성

  • diffOutlineAgainstGuidance() — LLM 1회로 절마다 keep(유지)/update(갱신)/new(신규) 분류. 응답이 비정상이면 전부 keep으로 취급(잘못 지우는 것보다 안전).
  • keep 절은 검색 없이 작년 내용을 그대로 통과시킨다 — update/new 절만 performSimilaritySearch로 아카이브 전체를 검색해 근거를 채운다.
  • 근거 부족 시 본문에 [자료 필요: 설명] 마커를 남긴다(draft.js의 "확인 필요"와 같은 원칙) — extractNeeds()가 이 마커를 정규식으로 뽑아 프론트의 클릭 가능한 버튼으로 연결한다.

신규 기준 파일 업로드

  • POST /workspace/:slug/doc-regen/upload-guidance — Collector로 파싱 → Document.addDocuments()로 워크스페이스에 바로 임베딩 → 기준 문서와 같은 분류를 DocumentClassification.confirm()으로 즉시 확정(검수 대기 없음) → 읽어낸 본문을 응답으로 반환.
  • 발견·수정한 버그: content_hash는 addDocuments가 임베딩하면서 계산해 workspace_documents 행에 써넣는다 — 업로드 직후 원본 파일을 그대로 읽으면 txt 등 일부 형식에서 비어 있어, 임베딩된 행을 다시 조회하도록 수정했다.

진행 상황 스트리밍

POST /workspace/:slug/doc-regen/stream — stream-chat과 같은 SSE 패턴. outline_start → outline → plan → (section_start → section_done)×N → done 순서로 이벤트를 흘려보내, 절이 많아 시간이 걸려도 진행 화면에서 무엇이 처리되고 있는지 실시간으로 보여준다.

빈양식 채우기 모드

  • POST /workspace/:slug/doc-regen/upload-template — upload-guidance와 파싱·아카이빙·분류확정 로직을 parseAndArchiveUpload() 헬퍼로 공유하지만, 반환값이 {title, pageContent, blocks}라 목차 추출에 바로 쓸 수 있다.
  • regenerateDocument({..., blankForm}) — blankForm이 있으면 목차 추출 대상이 기준 문서(baseDocs)가 아니라 이 서식이 되고(baseDocs는 넘겨도 무시됨, 선택 사항으로 강등), planFromBlankForm()이 diffOutlineAgainstGuidance()를 그대로 재사용하면서 결과의 "keep"만 전부 "update"로 강제 승격한다 — 빈 서식에는 보존할 기존 내용이 없기 때문이다.
  • /doc-regen/stream은 baseDocIds 또는 blankForm 중 하나만 있어도 동작하도록 완화됨.

빈양식 채우기 2단계 — 원본 .docx 서식 그대로

  • fillDocxTemplate() — 원본 word/document.xml의 기존 런/문단은 절대 안 건드리고, 각 필드의 라벨 문단을 찾아 그 바로 뒤에 새 문단만 추가한다(원본 서식이 깨질 위험을 최소화하는 설계). 앵커는 section.priorContent(원문 그대로 잘라낸 값, 더 정확)를 우선 쓰고 없으면 title로 찾는다.
  • POST /workspace/:slug/doc-regen/download-filled-template — {docId, sections}를 받아 Document.get() → workspace_documents → original_path로 원본을 서버에서 다시 조회한다(클라이언트가 경로를 직접 주지 않음, doc/raw와 같은 isWithin 가드). 확장자가 .docx가 아니면 명확한 에러.
  • DOCX만 지원 — HWP는 대상에서 제외. 이 프로젝트엔 HWP를 다시 쓰는 라이브러리가 없다(읽기만 가능). 바이너리 포맷을 직접 손대는 건 파일이 깨질 위험이 커서 시도하지 않았다 — HWP로 올린 빈양식은 1단계(구조화된 콘텐츠)로만 받을 수 있다.
  • 실제 GS25 빈양식(회사명/작성일/필수품목목록)으로 종단검증: 4개 필드 전부 각 라벨 바로 뒤에 정확히 삽입, 원본의 다른 내용은 전혀 안 바뀜을 확인.

문서함 폴더로 근거 검색 범위 좁히기

  • resolveFolderDocIds(workspace, folderKeys) — 사이드바의 굵은 스코프(전체/실적/법규/대외, resolveScopeDocIds)와 같은 패턴이지만, 문서함의 세밀한 업무분류→사업부 트리를 그대로 쓴다. "work:<업무분류>"(그 업무분류 전체) / "unit:<업무분류>:<사업부>"(정확히 그 조합)를 여러 개 겹쳐서(OR) 고를 수 있고, "전체"가 섞여 있으면 필터 없음과 동일하다.
  • 이 filterDocIds가 절 검색(performSimilaritySearch)에 그대로 전달돼, 지정한 폴더 안에서만 근거를 찾는다 — "작년 자료 참고 + 새 자료 반영"은 별도 로직 없이, 그 폴더 안에 두 종류가 같이 있으면 검색이 자연히 둘 다 찾아주는 구조다.

내부생성자료 순환 — 결과물이 다시 원자재로

초안(§07)·전사문서작성tool(§21)에서 만든 문서를 다운로드하면, 그 내용이 아카이브로도 자동 들어간다 — 단, 사람이 확인(승인)하기 전까지는 검색에 절대 쓰이지 않는다는 원칙을 지키면서.

  • server/utils/classification/generatedDocs.js — resolveUnapprovedGeneratedDocIds()가 workType == "내부생성자료"이면서 status != "confirmed"인 문서의 doc_id 목록을 돌려준다. 이 목록에 없는 모든 문서(=기존 업로드 전부)의 기본 검색 동작은 전혀 안 건드린다 — 좁게 적용되는 게이트.
  • PGVector.performSimilaritySearch가 dense/lexical 후보 둘 다에서 이 목록을 걸러낸다(#excludeDocIds) — 1등 문서로 랭크되더라도 예외 없이 제외.
  • POST /workspace/:slug/archive-generated — 다운로드된 markdown을 parseAndArchiveUpload()(§21의 그 헬퍼, 세 번째 호출부)로 그냥 임베딩만 하고, DocumentClassification.upsertProposal()로 workType="내부생성자료"·status="proposed"만 만든다 — 절대 자동 확정 안 함. 분류 검수 화면에서 사람이 평범하게 "확인"을 누르면 그 즉시 검색 대상이 된다.
  • 파일명은 문서 제목 그대로(금지문자만 제거) — 다운로드하는 사람이 알아볼 수 있게.
실제 라이브 검증: 업로드 → "제안" 생성 확인 → 검색에서 제외됨 확인 → 검수에서 확인(confirm) → 그 즉시 검색에 포함됨까지 전부 API로 직접 확인했다.
