재구축 실행 결과 — P0–P5

v14의 종합 진단에서 정한 방향대로 P0–P5를 실행했다. stock AnythingLLM 검색 위에 쌓였던 커스텀 5겹을 걷어내고, 임베딩 모델을 이 머신에 맞게 교체하고, 적재·삭제를 다시 세우고, 파일 4종(+xls)의 구조 추출을 고치고, 실제 사내 코퍼스 68문서로 검증했다. 이 문서는 무엇이 어떻게 바뀌었고 실측이 어떻게 나왔는지를 기록한다. 전체 아키텍처 레퍼런스는 v13, 진단·의사결정 근거는 v14.

01

재구축 개요

v14에서 승인한 5개 결정(단일 워크스페이스 + 태그 뷰 / sensitivity 프로토타입 보류 / bge-m3 → multilingual-e5-small / docling-optional / 과감한 재작성)을 P0–P5로 실행. 6개 커밋.

P0 클린 슬레이트 + 모델 교체

  • 임베딩 Xenova/bge-m3(1024d) → MintplexLabs/multilingual-e5-small(384d). bge-m3는 이 머신 여유 메모리(~1.7GB)와 ONNX 피크가 정면 충돌해 쿼리 임베딩이 조용히 실패하고 있었다. e5-small은 메모리 가드가 없고(assertLoadMemory는 bge-m3 전용) 웜 임베딩 111ms/2청크(bge-m3 4.8초). query:/passage: 프리픽스는 native embedder가 이미 처리. bge-m3는 주석으로 남김 — 서버 이전 시 복귀.
  • 워크스페이스 5개·문서 113·벡터 2,718·분류 185·채팅 171 → 전부 0. pgvector 테이블 DROP(첫 임베딩 시 384d 재생성). storage 3개 폴더 + collector/hotdir 비움.
  • 단일 워크스페이스 archive-full(전사 아카이브, topN 12, similarityThreshold 0.15, vectorSearchMode default). slug는 archive-full 고정 — 커스텀 프론트가 slug === "archive-full"로 커스텀 UI를 스위치.

P1 검색 파이프라인 재작성 72521f98

  • 제거: #preferLexicalDataMatches — 질문에 숫자나 실적·금액·수량류 단어가 있으면 키워드(ILIKE) 매칭을 의미검색 위에 강제로 올려, 합성 lexical 점수가 실제 e5 코사인보다 높게 나와 최종 절단에서 의미검색 결과를 밀어냈다.
  • 제거: 조용한 dense→키워드 강등 — 쿼리 임베딩 실패 시 이제 명시적 abort 메시지.
  • 제거: 섹션 확장을 되돌리던 사후 재절단.
  • 추가: 문서별 청크 상한(SEARCH_PER_DOC_CAP 기본 3) — 결과가 여러 문서에 걸침. P5에서 "최상위 1개 문서는 상한 면제"로 보정(§05).
  • 추가: 합집합 전용 lexical 병합 — dense가 놓친 문서만 뒤에 붙임, dense 순위 불변.
  • 추가: filterDocIds 파라미터(P4 업무별 뷰 필터 배선).
  • 수정: distanceToSimilarity — distance ≥ 1 → 유사도 1이 정반대 벡터를 완벽 일치로 채점하고 있었다. 1 - distance를 [0,1] 클램프.
  • 새 파이프라인: 임베딩(query: 프리픽스, 실패 시 abort) → 광역 dense 후보(K ≈ max(topN×5, 60)) → 문서별 상한 → 합집합 lexical 병합 → topN 절단 → 예산 제한 섹션 확장.

P2 적재 단일화 · 삭제 완결 · 재구축 58463310

  • 파일명/제목 중복차단 제거 — 사내 아카이브는 이름이 겹치는 다른 문서(붙임.pdf·보고서.pdf)가 많고 조용히 스킵하는 게 중복보다 나쁘다. 바이트 동일(content_hash)만 스킵.
  • embedding-worker.js가 상대경로 docpath 저장 + blocks 배열 제거 — in-process 경로와 정확히 일치. 두 경로가 docpath 형식이 달라 removeDocuments의 조회가 worker 적재 문서를 놓치던 "지웠는데 안 지워짐" 버그.
  • removeDocuments: basename 폴백 + opts.purgeSource(다른 워크스페이스가 참조 안 하면 파싱 원본 파일 + vector-cache 삭제).
  • pgvector.deleteDocumentFromNamespace가 추적 행뿐 아니라 metadata->>'doc_id'를 직접 sweep — orphan 벡터 backstop.
  • 신규 Document.rebuildWorkspace + POST /workspace/:slug/rebuild — 상태가 꼬였거나 임베딩 모델을 바꿨을 때의 복구 액션.

P3 파일 4종(+xls) 구조 추출 — docling 없이 aa1d6a01

  • XLSX 재작성: 워크북 1개 = 문서 1개(한글 시트명이 slugify 후 빈 문자열 → 시트 파일 충돌 클래스 소멸). 각 시트 = block_type:"table" 블록 + section_path = 시트명, finalizeBlocksDoc 경유. 헤더 감지는 "첫 ≥2셀 행"으로 일반화 — 하드코딩 문자열 제거. .xls 추가.
  • DOCX: LangChain DocxLoader(평문 한 덩어리) → mammoth HTML → 블록(h1–h6 → section_path, 표, 리스트).
  • PDF(pdf.js): PDFLoader가 줄 폰트 크기 보존 → linesToBlocks가 큰 줄/구조마커(제N조, 1.2.1, Ⅲ.)를 헤딩으로 표시 → buildSectionPaths. 법률 PDF가 docling 없이 제N장 > 제N조(제목) 계층(실측: 법률 71청크/53경로, 판매장려금 지침 40청크 4단 중첩).
  • HWP/HWPX: 자체 파서 유지 검증(유통혁신.hwp 33청크 전부 중첩 section_path).

P4 업무별 뷰 필터 + sensitivity 해체 a8a337ca

  • 사이드바 스코프(전체/실적/법규/대외)가 UI-only였던 것을 검색에 배선 — 스코프 → doc_type 집합 → content_hash → doc_id → filterDocIds. 법규 = 법령·행정규칙, 실적 = 실적자료·보고서·계획서·교육자료, 대외 = 협약서·계약서·제안서·회의자료·품의서. 채팅(browser+thread) + v1 검색 API 전부.
  • sensitivity dormant — retrieval/access를 게이팅한 적이 없고 분류 검수 흐름에만 관여했다. _isComplete가 더 이상 sensitivity 요구 안 함, confirm()이 거부 안 함.

P5 실코퍼스 적재 + 검증 + 튜닝 6485bc03

  • _samples/ 70개 → archive-full 68문서(바이트 동일 2건 스킵). parse_path: pdfjs 52 / ocr 5 / xlsx 5 / hwp-parser 3 / hwpx-owpml 1 / docx-mammoth 1 / pptx-text 1.
  • 68문서 전부 claudecli 분류(§04).
  • 실측에서 완전성 격차 발견 → 튜닝(§05).

완전성 격차 — 진단과 수정

튜닝 전: 정답 문서는 매번 검색됐지만(retr-hit 1.0), "판단기준을 전부 알려줘"류 질문이 5개 중 2개 사실만 답했다(완전성 0.2). 원인 두 가지:

① 문서별 상한 3이 "그 문서가 곧 답"인 경우를 굶겼다수정됨
판매장려금 지침의 III. 판단기준 섹션은 34청크(기본장려금·성과장려금·무반품·재고소진…)인데, dense는 헤더성 청크 3개만 상위로 올렸고 상한 3에 걸려 그게 전부였다. 수정: #capPerDocument가 최상위 1개 문서는 상한 면제(최대 40청크), 2위 이하만 상한 적용.
② 섹션 확장이 큰 섹션을 건너뛰었다수정됨
expandSections가 16k자 넘는 섹션은 스킵했는데, 판단기준 섹션이 ~34k자라 정확히 그 케이스였다. 수정: 섹션 상한 16k → 40k, 총 예산 32k → 50k. LLM이 claudecli(대형 윈도우). 결과: jangryeo-axes 완전성 0.2 → 1.0.

06

알려진 한계

  • 이미지 기반 문서 5건 + 이미지 PPTX 1건 — 스캔 협약서·체크리스트·라벨 증빙. 현재 플레이스홀더로만 색인. Gemini 비전 인입(P1d, Google API 재제공 대기)까지 본문 없음. 증빙/첨부 성격이라 핵심 지식은 아님.
  • docling-optional — 기본은 경량 파서. docling은 중요 문서 수동 옵트인. 이 머신에서 느리고 불안정했던 이력.
  • e5-small — bge-m3보다 한글 변별력이 약간 낮다. 순위 + 섹션 확장 + grounded 프롬프트로 보완. 서버 이전 시 bge-m3 복귀.
  • hwp-innovation류 — 사실이 여러 섹션에 흩어진 큰 문서의 완전성. 섹션 확장이 계층형 지침만큼 안 먹음.
  • sensitivity 접근통제 — dormant. 필터 수준이라 네임스페이스 분리보다 약함. 실제 통제 요구 시 별도 네임스페이스.
  • 골든셋 stale — archive.answers.jsonl이 4문서 archive-test 기준. 큰 코퍼스에서 재작성 필요.
